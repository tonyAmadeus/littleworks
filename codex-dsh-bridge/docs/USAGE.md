# 使用与验收

## 窗口路由

| 情况 | 路由 |
| --- | --- |
| 回复实际收到的消息 | 保持父消息，回该消息的来源窗口 |
| 主动发起并指定目标 | 使用所指定的真实对方窗口 |
| 主动发起，未指定目标，本窗已配对 | 使用当前窗口登记的配对 |
| 主动发起，本窗无配对 | 已授权自动创建时新建对方聊天，否则要求指定目标 |
| 人工暂停 | 只暂停当前窗口选中的配对，其他配对及监听继续 |
| 自然待命 | 保留监听和绑定，人类明确新话题可继续 |
| 人工暂停后的继续 | 通过本窗 resume 入口恢复，跳过暂停期间历史 |

同一个 Codex 窗口可以登记多个目标，但暂停默认作用于当前选中的一对。多目标时明确说明目标窗口，必要时由助手在后台使用实际 conversation 编号选择。接收和查询回执不会更改当前选择，不能用“最近聊天窗口”猜测一条回复的目的地。

## 对话与收尾

主动发送示例：“告诉 DeepSeek：请从工程角度评价这个方案。”DSH 对应：“告诉 GPT：请帮我核对这个结论。”明确暂停可用“先停一下”“别聊了”，恢复可用“接着聊”“恢复对话”。问“如何暂停”或引用这些话，不触发暂停。

没有发言总数或回复链上限。单条正文仍受现有接口的 12,000 字符限制，传输还有大小和超时限制；长内容应以结果文件或明确分段交付。双向 AI 讨论会消耗账户用量，使用者可随时人工暂停。

自然收尾使用隐藏 propose/accept/reject：一方检查目标、问题、交付、待办和投递后提议收尾；另一方核对后接受或指出遗漏。最后确认实际被观察到才进入待命，不形成确认消息链。语义完整性依赖两端模型的判断，程序主要检查消息、待交付状态和父消息；它不能机械证明答案无遗漏。

## 安装验收

1. 在 Codex 窗口 A 明确向 DSH 发一个简单问题，确认 DSH 对应窗口出现完全相同的正文。
2. 从该 DSH 窗口回答，确认回答回到 A。检查后台回执，接口接受和实际观察的状态应能区分。
3. 新开 Codex 窗口 B，发起另一段互聊，确认拥有独立配对；从 A 发“先停一停”，检查 B 仍能回复且监听仍运行。
4. 在 A 明确恢复，确认暂停期间旧正文没有被重放。
5. 从一个未配对的 DSH 窗口主动联系 GPT，检查授权的新 Codex 窗口创建或指定目标绑定。
6. 让一个完整话题自然收尾，核对双方末句实际接收后待命，没有额外确认往返；由人类发起新话题，检查原绑定继续可用。
7. 重启两款桌面应用后明确联系，检查按需监听恢复，人工暂停的配对仍保持暂停。

验收使用者自己选择的短消息。此过程会真实调用两端模型，不能用离线测试或依赖检查代替。
